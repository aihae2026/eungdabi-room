# 양식별 제출 대상 기관

## 적용 범위

- 양식 관리 권한은 기존과 동일하게 통합관리자만 갖는다. 그룹관리자/운영담당자에게 새 양식 관리 권한을 부여하지 않는다.
- 신규 양식은 기본적으로 전체 활성 운영담당자 기관을 대상으로 한다.
- 전체 대상은 신규 기관도 포함하며, 선택 대상은 선택한 기관코드만 포함한다. 그룹은 검색용이며 그룹 자체에 배정하는 기능은 아니다.
- 작성 중에는 양식 저장에 함께 반영한다. 운영 중에는 별도 제출 대상 저장 버튼으로 대상만 변경한다. 종료 양식은 변경하지 않는다.
- 검색 결과 전체 선택은 현재 필터의 활성 기관을 추가 선택한다. 선택 전체 해제는 숨겨진 선택까지 모두 해제한다.
- 최소 1개 선택을 요구한다. 이미 선택된 기관의 비활성 상태는 표시·유지할 수 있지만 실제 제출은 차단하며, 비활성 기관을 새로 지정할 수는 없다.
- 복사본은 원본의 대상 제한을 보존한다. 운영담당자의 그룹 소속 변경은 기관별 지정에 영향을 주지 않는다.
- 기관별 목록, 양식 상세, 제출 API와 DB INSERT 트리거에서 대상/활성/운영 상태를 검증한다. 클라이언트가 보낸 기관코드가 아니라 인증된 세션의 기관으로 제출을 저장한다.
- 대상 제외는 신규 제출만 제한한다. 제출 이력, 응답, 집계/분석 권한은 변경하지 않는다.

## DB 반영 (이번 작업에서는 실행하지 않음)

변경 SQL: `supabase/migrations/20260915145425_checklist_submission_targets.sql`

운영 반영 승인 후 DB 백업 및 현재 스키마를 확인하고, **DB 변경 → 새 코드 배포 → 운영 통합 확인** 순서로 진행한다.
기존 양식에 `all`/빈 배열/버전 0을 부여해 기존 운영담당자 기관의 제출 허용 범위를 보존한다.
`schema.sql`은 기존 기준 스키마이며 신규 DB에도 기준 스키마 다음 이 마이그레이션을 적용해야 한다.
컬럼 변경은 트랜잭션 내에서 수행되고, 기존 submissions/answers를 변경하거나 삭제하지 않는다.
서비스 역할만 양식 테이블에 접근하며 공개 역할에는 새 권한을 부여하지 않는다. 신규 함수는 SECURITY INVOKER로 정의한다.
DB는 양식 및 기관 행을 FOR SHARE로 잠근 상태에서 신규 제출을 검사한다. 대상 변경/운영 종료/기관 비활성화와 제출의 순서를 직렬화한다.
기존 스키마/코드와 같은 기관코드 식별자를 사용한다. UI에서 기관코드 변경은 지원하지 않으며, 향후 DB에서 코드를 일괄 변경할 때는 대상 배열도 함께 이관해야 한다.
